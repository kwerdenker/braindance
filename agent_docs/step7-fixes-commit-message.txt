Close what review found in the recorder, and in the checks that missed it

Step 7 landed with ten defects a review then demonstrated, and fixing those
introduced one more that cost footage. Four rounds in, the useful pattern is not
the count: almost none of these were wrong logic. They were checks asserting a
condition they did not bring about, and code whose comment described an intention
rather than the code beneath it.

Two corrections to that commit's own body while this is being written, because
both were false when claimed. The low-space skip did not carry "1 claim unproven
here" into its verdict - it reached the assertion-count line and nothing else, so
on every platform but this one the run printed an unqualified PASS and exited 0
with the claim never exercised. And the route control it described was not the one
CLAUDE.md specifies. Both are fixed below and both were found by someone running
the thing rather than reading it.

A third review round found thirteen more, and the shape of the fix matters more
than the count. Six of them were the same defect wearing six paths: a route that
changed something while dispatching on the path alone, with readBody resolving an
empty object for a request that had no body - so GET /record/stop ended a shoot
and disarmed the node, and an <img src> or a link prefetch on any page anywhere
was enough to send it. Fixing six routes would have left the seventh outside the
list. The ladder is now a table that *is* the dispatch: having a write handler is
how a route declares that it changes something, and the dispatcher puts every one
of those through a single gate that requires the method, a same-origin caller and
a JSON content type. Those three together are what a page you merely visit cannot
produce, since a no-cors fetch may only set three content types and an HTML form
the same three.

Enumerating found ten mutating routes where poking at them one at a time had
found six - /library/delete/:id, /library/sync-marks/:id, /record/mark and
/presets/:name were never in anyone's list. That is the argument for the table
stated as a number. The table is served at /library/routes, derived from the
dispatch rather than restated beside it, and the check walks it asking each route
three questions with one row per term, so a route added next year is asked by
existing. The falsification control has to be a mutation that adds a mutating
route without registering it: stop-route-reads moves /record/stop's handler into
the read slot, and what catches it is the arm that drives all eighteen
GET-answering routes against a recording server and asserts the recorder did not
move.

An absent Origin passes, and that is load-bearing rather than lax. Every call
across the capture-node link is a server-side fetch - the manifest, the marks log,
the take's bytes, the reclaim's delete - and none of them carries an Origin header
at all, because nothing in Node has an origin to declare. Requiring one would
sever the two-machine link and present it as a reconciliation failure. What the
header is good for is the case it exists for: a browser saying which page this
request came from, where a wrong answer is decisive and no answer is simply not a
browser.

Recording on a replay server was refused rather than fixed, and the reason is
better than the bug report. A replay loops, so frame 0 follows the last frame and
the stamps go backwards - and one take is one continuous stream with monotonic
stamps, which the index, the retime curve and mixT all rest on. No amount of
making it "work" produces a take, so the button disables itself. Two things came
out of looking: the tick now supplies raw through encodeMessage, restoring an
invariant handleMessage documents, and broadcastFrame moved ahead of
recorder.write so a recorder problem can never take the monitor dark.

Backpressure drops rather than blocks, which loses frames on purpose and is the
lesser loss. A write that awaited drain would stall the same stdin pipe this
document already measured: a connected viewer costs the take about 11% of its
frames because backpressure reaches the grabber, which then cannot service USB in
time. Blocking on disk would do the same thing for the same reason, and those
frames never reach the file at all. So past a stated 64MB ceiling - about 130
frames, four seconds at full rate - frames are dropped and counted, which is the
stance broadcastFrame already takes, and a KNCT take with a gap still replays at
the cadence it was shot at. frames and bytes now come from stream.bytesWritten
through a bounded in-flight queue, so both mean durable rather than accepted.
Probed with a 300-frame synchronous burst, which is a fixture rather than a race:
nothing can drain during a synchronous loop. Mutated, the peak is 145.9MB against
the 67MB ceiling and the monitor reports 67,594,059 bytes with nothing on disk.

That fix was wrong in a way only a fourth round found, and it is the most useful
thing in this commit. The queue it introduced was drained in one place - the
getter something calls when it wants state - so nothing removed an entry until an
operator opened the monitor, and the drain that finally ran was shift() in a loop.
The comment above it said the queue was "bounded by the buffer ceiling rather than
by the length of the take", which was the intention rather than the code. Measured
on 486KB frames, interleaved, three repetitions per length, median: 48.9ms at
27,000 frames and 3,677ms at 216,000, about 4.1x per doubling. The falsification
control is what makes that a measurement rather than a timing - the identical
drain taken with a moving head index instead of moving the array stays under a
quarter of a millisecond throughout, so the cost is shift() and not the loop.
Confirmed independently on a second machine at 7.6s where this one gives 3.7s:
magnitude moves with load, the 4.1x does not.

A stall is not a stall here, and that is why it was worth a round. It is
synchronous, so nothing services stdin while it runs, and this document has
already measured what that does - backpressure reaches the grabber, the grabber
misses USB service windows, and the device drops depth packets that no download
recovers. So the trigger is somebody walking up to an unattended node and opening
the panel to check on it, which is the one moment the take can least afford it.
The mechanism is demonstrated in-process against the same settle() the HTTP
handler calls; device-side drops were not measured, there being no sensor on this
machine, so the magnitude is the spec's and the spec flags its own 11% as
sequential rather than interleaved.

The fix makes the comment true instead of the other way round. write() drains on
every frame, which is what actually bounds the queue to the ceiling, and settle()
advances a head and drops the consumed prefix in a single splice only once that
prefix is as long as what remains - so it copies at most one element per element
ever queued. Deepest 1 live entry after 20,040 frames. The failure branches
inherit the bound rather than relying on the queue happening to be small by the
time they run, which is the difference between bounding a queue and speeding a
drain, and it is worth saying which was built. The frame path is unmoved:
0.029us/frame before against 0.031 after at 27,000, 0.030 against 0.031 at
216,000, flat across take length, so the cost was removed rather than relocated
onto the loop that can least afford it. The replacement arm asserts queue depth
rather than wall-clock, because two rigs disagreed by 2x on the same code.

Dropping now pushes at the transition and deliberately not at the recovery.
Footage is being lost for every second of the five the panel's poll would
otherwise take to notice, and a node with nobody watching is exactly where this
starts - while a readout that stays red until the next poll costs nothing, where
one that goes green early costs the take.

An observer effect in the instrument is now its own entry in CLAUDE.md, because
it is a distinct failure from the ones already there - not a probe in a dead zone
and not a vacuous assertion, but a probe that changes the state it samples.
Polling the library to wait for a take to finish scans the take still being
written and writes it a sidecar, so "a sidecar exists" stopped meaning "finished"
the moment anything asked. It came in at 10 and 11 frames on two runs and had been
firing on four unrelated mutations. The same shape turned up a second time in this
step's own check, where replay-handle-evictable cleared the socket's status list
after the skims and discarded the lost-sensor report it was about to assert on.

Three of this step's own arms turned out to pass builds that were wrong in exactly
the way the arm existed to catch, and the enumeration was the worst of them. The
paragraph added to CLAUDE.md a round earlier says the falsification control has to
be a mutation that *adds* a mutating route without registering it. The control
shipped moved an existing one instead, and what caught it was a floor written as
`mutating.length >= 10 && writeOnly.length >= 7` - today's values, so a move trips
them and an addition cannot. A review planted a handler doing PROJECTS.write in a
read slot: 241 assertions, none failed, exit 0, and the file on disk afterwards.
The reason is the agreement rather than the arm - the sweep spawned its server
with no --projects and no --presets, so those stores lived outside the directory
it snapshotted, and it substituted the *recording* take's id into every :id, where
beingRecorded() answers 409 before the handler runs, so five of eighteen routes
were counted as driven and never executed. The floor is gone, replaced by a
coverage row and a reached-past-the-409 row; the server gets both stores inside
the snapshot, an open take and a closed one, GET and HEAD, names that exist and
names that do not; and read-route-writes is the control the document asked for.

A pair of readings cannot see a handler that writes and restores inside one
request, and no widening of the snapshot fixes that, so the resource is
instrumented instead of its contents: DocumentStore and the marks log carry
monotonic counters, served as a read route the sweep drives like any other, and a
counter cannot be restored. read-route-restores fails only the count row while the
snapshot row keeps passing, which is what makes the counter load-bearing rather
than a second way of saying the same thing.

The first version of that plant was dishonest, and CLAUDE.md has a new paragraph
because of it. Write-then-restore with utimesSync failed both rows - but APFS
keeps modification times to the nanosecond and a Date carries milliseconds, so
what failed was the 0.13ms the restore could not put back, 1785523816453.8726
against 1785523816454. On a filesystem with coarser stamps the same plant walks
through, so the control was asserting the platform. The rule is the converse of
one already there: before believing a mutation was *caught*, confirm it was caught
for the reason claimed, because a control that reddens incidentally reads as
coverage and is worse than a missing one. The plant is now write-then-remove,
which touches nothing that survives and depends on no filesystem.

The ceiling had the same shape. The row asserted the observed peak against
MAX_TAKE_BUFFER imported from the build under test, so a ceiling of 8MB passed all
241 assertions printing "peak 8.8MB against a 8MB ceiling", and the number
deciding how much footage a stutter costs was unmeasured. It now asserts an
absolute the build cannot move - 139 frames at an observed 475KB mean is 67.6MB
accepted before the first drop, 0.7% off the 64MiB written as a literal in the
check, and 4.63s against the four seconds of ride-out the ceiling exists to buy.
The frame size is observed from bytes the check saw rather than imported, because
recomputing the ceiling's own arithmetic would have been the same defect one level
down.

And a wait was inverted. Section 4c broke on armed === false, true from boot on a
server started without --record, so it granted a fixed 255ms while its comment
claimed it waited for the hello - against a sensor going live at 257 to 506ms, a
negative margin on five runs of five. It waits on a binary frame off the live
socket now, because /record/state reports what the operator asked for rather than
what the sensor is doing. A gate that reddens for reasons unrelated to what it
tests is how people learn to re-run until green.

Two shapes the route sweep still cannot see are named in its own comment rather
than left for the next plant to find. A handler that writes and restores inside
one request is invisible to any pair of readings taken outside it - which is why
the counters exist, and the counter closes it - but a handler gated on a query
parameter is outside the *drive* rather than the snapshot, and no enumeration of
the table can reach a parameter the table does not declare. That one is recorded
as unclosed.

One decision here narrows step 9 rather than contradicting anything, and it is
written down so a later step does not rediscover it. The spec assigns "the monitor
has to negotiate decimation while recording" to step 9, and the manifest fix means
the take being written now answers 409 on its capture routes - so decimated frames
cannot be pulled over HTTP for the take in progress and that negotiation has to be
socket-side. The live fan-out is untouched, so nothing there is harder; one avenue
is closed deliberately, because scanning a file being appended to cost a full read
and a sha256 per request.

Verified on a frozen tree. Five executable files checksummed before the sweep and
after, byte-identical both times; CLAUDE.md moved once mid-run and is the one file
in the change that nothing under tools/, server/, web/ or native/ opens - the only
occurrences anywhere are four comment references inside library-check itself, so
the tree the sweep exercised did not move even though the documentation beside it
did. Eight clean runs green - index 42, registry 53, timeline 63, keyframe 131,
export 35, library 251, and both determinism arms. All 85 declared mutations
caught, judged by failed-assertion count rather than exit code, with the mutation
list taken from each tool's own refusal message rather than a list written beside
it: library-check grew from 18 mutations to 44 across these rounds, and a
hardcoded list would have swept 59 of 85 and reported a clean pass.

Every mutation whose anchor text these edits moved was re-checked rather than
assumed. Driving each one with a deliberately missing --capture builds the
mutation at module load and fails before the fixture is read, which turns "did an
edit break an anchor" into one cheap total answer: 43 matched exactly once, then
44 after /library/writes landed a line from read-route-writes's anchor. The two
mutations anchored in the rewritten settle() and write() were confirmed by running
them, 2 failed rows and 1, rather than by checking their text survived.
